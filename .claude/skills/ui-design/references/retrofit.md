# 既存アプリの見た目を、壊さずに刷新する

動いている業務アプリを、利用者の作業を止めずに新しい見た目へ移すときの手順と、実際に起きた落とし穴。

## 手順

1. **JS が参照している ID とクラスを洗い出す**（`getElementById` / `querySelector` / `onclick` の文字列）。刷新後もこれらは必ず残す。見た目のために不要になった要素も、`hidden` で残してから外す。
2. **新しいスタイルは別ファイル（例: `ui.css`）に書き、既存の CSS の後に読み込む**。既存のスタイルは消さずに上書きする。
3. **共通部品を先に作る**: 通知（`alert` の置き換え）、確認ダイアログ、シート、空状態。`window.alert` をトーストに差し替えれば、既存コードの呼び出しを書き換えずに全画面で効く。
4. **画面ごとにマークアップを差し替える**。一覧の描画関数（HTML を組み立てる JS）は、元の関数を同じ名前で置き換えるか、描画先だけを新しくする。保存・削除などデータを書く処理は既存の関数をそのまま呼ぶ。
5. **区切りごとに確認環境で触ってから次へ**。確認用 URL は固定にしておくと、確認を頼む相手に毎回伝え直さずに済む。
6. **文言は変えない**。変える場合は利用者向けの一覧に載せる。

## 落とし穴（チェック項目）

- [ ] **JS が後から注入するスタイル**（`<style>` を JS で追加する古いコード）が新しい見た目を上書きしていないか。例: `.tab-content { display: none }` が注入され、初期表示のタブが空になった
- [ ] **インラインの `<style>` や `!important`** が残っていないか。上書きには ID を含む強いセレクタか `!important` が要る
- [ ] **JS が要素の `style.display = 'block'` を直接書いていないか**。flex の部品が崩れる。表示に戻すときは `style.display = ''` にする
- [ ] **同じ名前のグローバル関数が複数ファイルにないか**。後から読まれたファイルの関数が勝ち、引数の順番が違うと中身が入れ替わる（例: `downloadCSV(中身, 名前)` と `downloadCSV(名前, 中身)`）
- [ ] **タブを切り替える処理が、共通のクラスを持つ要素をページ全体でまとめて隠していないか**。別のタブを経由すると、開いたタブの中の表まで隠れたままになる。データは入っていて合計も合うので気付きにくい（例: 従業員管理を開くと全ページの `.attendance-table-container` が隠れ、そのあと開いた経費精算の表が出なかった）。タブを開く側で、そのタブの中の要素を表示に戻す。確認は「直接開く」だけでなく「別のタブを経由して開く」でも行う
- [ ] **同じ表示先に書き込む処理が 2 つないか**。片方が少し遅れて動くと、もう片方の結果を上書きする（例: 月の一覧を、直近 3 日の読み込みが上書きした）
- [ ] **データの検索が DB の索引を必要としていないか**。条件と並び替えを同時に指定すると、索引の無い環境（確認環境など）で失敗する。件数が少なければ条件を減らして画面側で絞り込む
- [ ] **日付を `toISOString()` で作っていないか**。UTC になるので日本時間の朝 9 時前は前日になる
- [ ] **画面の読み込み時に外部サービスの認証を走らせていないか**。ログインのたびにポップアップが出る
- [ ] **キャッシュで古い画面が残らないか**。JS / CSS の URL に版番号（`?v=日付`）を付けて更新ごとに変える。確認環境のホスティングは HTML / JS / CSS を `no-cache` にする
- [ ] **絵文字が JS の中に残っていないか**（選択肢の文字列、通知、空状態の文言）。`grep` で探す
- [ ] **書体がボタン・入力欄・表・JS が作る通知にまで効いているか**
- [ ] 刷新前から呼ばれていない表示関数（例: 氏名の表示）が無いか。刷新で目立つようになる
